SUMWhat happened

The architecture is in place and the pilot works end to end in a real production build: compress-pdf submissions return a job record in about 10 ms instead of holding the request open for the length of a Ghostscript run, and the same request with the flag off still takes the legacy path byte for byte. All seven validation gates pass. Every local tool still processes in the browser and creates no job.

Four things were found along the way, and two of them are still open on purpose. Both fixed items were real defects with silent failure modes; both open ones are pre-existing gaps whose repairs require changes this phase was explicitly told not to make. They are written up in full below rather than folded into a summary line, because in both cases the honest version is more useful than the tidy one.

One process note that matters more than any single result: a green test run turned out not to be proof of a green test suite. The suite reported all-pass, then failed on a later identical run — an intermittent failure in my own integration test, caused by colliding job identifiers rather than by the code under test. It is fixed at the root and pinned by a deterministic assertion, and the whole suite was then run repeatedly rather than once.

FINDFindings

Ordered by what a user would notice, not by when I found them.

A

The pilot silently dropped the compression result summary

Fixed

A job that compressed a file to 79% of its original size rendered a bare “Your file is ready” with no numbers at all, while the legacy runner it replaces showed the comparison. Nothing errored and no test failed — the panel guards its size display on outputBytes != null, so absent data renders as absent UI.

The counts were dropped in two independent places: the status projection never carried them onto the wire, and the pilot runner passed the literal outputBytes={null} into the panel. Either one alone would have hidden the display, which is why the fix touches three layers — the wire type, the projection, and the runner — and why showSizeComparison: true being set for this tool is what proves the display was intended rather than optional.

before job 10250 → 8118 bytes, panel: "Your file is ready" after panel: "10 KB → 7.9 KB (21% smaller)" tests 6 added · mutation M-c 2 kills · M-d 1 kill probe 39/39 in the production build

The regression test asserts the projection carries the counts and still withholds storageKey, outputKey, ownerId, userId, workspaceId, payload, result and processorMessage — the point was never “send more”, it was “send sizes, which say nothing about contents”.

C

The legacy job routes perform no ownership check

Open · pre-existing

This is the most serious item in the report and it is not a pilot regression — it sits on the pre-existing path and is reachable in production today. A caller with no session can read any legacy job's status and download its output. I verified it rather than inferring it: I gave a completed legacy job an owner, then fetched it from a fresh cookie jar.

job owner set to user/owner_alice stranger GET /api/jobs/{id} → HTTP 200 (full status) stranger GET /api/jobs/{id}/download → HTTP 302 → signed URL stranger follows the signed URL → HTTP 200 78,359 bytes %PDF-1.5 same stranger, a PIPELINE job: GET /api/jobs/{id} → 404 GET /api/jobs/{id}/result → 404 POST /api/jobs/{id}/cancel → 404

The pipeline path is correct — it resolves the actor server-side, requires an owner match, and returns 404 rather than 403 so job ids cannot be enumerated by probing. The legacy branch of the same two route files simply never resolves an actor. The routes' own comments already describe this split, one of them calling the legacy behaviour unauthorized in as many words.

I did not fix it, and the reason is not scope alone. Legacy jobs are created anonymously with ownerType and ownerId both null, and the ownership predicate correctly treats a job with no owner as belonging to nobody. Adding the check as a one-line guard would therefore make every anonymous legacy job undownloadable by the user who just created it — trading a disclosure bug for a total outage of the pre-pilot runner. It needs an anonymous-ownership token or an owner backfill, which is a design change to the legacy path this phase was told to leave intact. It should be the next piece of work.

B

Content-Disposition does not survive the redirect to storage

Deferred · scoped

Both the pilot and legacy download routes set Content-Disposition on a 302, and a redirect's headers do not survive being followed. Neither the local signed-URL route nor an R2 presign carries one — the presign builds a bare GetObjectCommand with no ResponseContentDisposition — so the header reads null for both runners, in dev and in production alike. The pilot did not regress this; the legacy route has the same shape and its own comment calls the header a best-effort hint.

Fixing it properly means adding a download-name parameter to the signed-URL port, which is a storage-architecture change this phase forbids. Forcing attachment on the shared storage route was the other option and is worse: other consumers use signed GETs for inline viewing, including the editor loading PDFs. The download still arrives with a correct filename derived from the submitted name, which is why this is a defect and not a broken feature.

Extension point: ISignedUrlService.signedUrl(key, verb, ttl) — add an optional response-disposition argument there and both runners get correct filenames from one change.

D

Colliding job ids made a cleanup test blame itself

Fixed

The suite reported a leaked scratch directory after a job finished. It had not leaked — the shared scratch root was empty after every run, and the failure named a different test each time. The in-memory job repository mints ids from a module-level counter that restarts at 1 in each process; the test runner runs files in parallel forks against one machine-wide scratch root; so two forks both mint inmem-job-11, and a directory belonging to a sibling test file matched this job's prefix. Observed directly in the live root: inmem-job-11 held three distinct directories at once.

The fix adds per-process entropy to the identifier rather than loosening the assertion, because two repositories handing out the same id is the actual defect and a work directory is only the first thing to trip over it.

What makes this worth reporting is the second half. Reverting the fix and running the full suite twice did not reproduce the failure — the race needs a specific interleaving, so the surviving mutant proved the suite could not defend the invariant it had just failed on. A guard that reproduces two runs in three is not a guard, so the invariant is now asserted directly: loading the module twice stands in for two processes, since the counter is module state.

before fix full suite 2 runs → 2 failures (different test each time) after fix full suite 4 runs → 4 × 263 files / 5,522 tests pass mutation M-e bare counter → killed M-f constant tag → killed M-g base64 tag → survived; proven a weak mutant (base64 of "0.xxx" is always alphanumeric) M-g2 tag = "a/../b" → killed (2 of 3 assertions)

M-g is included because it survived. Chasing it down showed the mutant never violated the invariant rather than the test failing to catch it — and the path-safety assertion it was meant to test does fail correctly on a genuinely unsafe identifier, which matters because these ids become directory names and storage key segments.

29Security review

Every item evidenced from source; the last three tested empirically against a running production build.

  • ✓No shell concatenation of user input. execFile with an argv array and no shell, so nothing a user supplies can be reinterpreted as a command.
  • ✓Identity resolved server-side. The actor comes from resolveJobActor(); the port's own documentation states it is never read from a request body. No userId, workspaceId or owner is trusted from the client.
  • ✓Ownership is strict on three points. A job with no owner belongs to nobody, ownerType must match, and workspace scope must match.
  • ✓Job ids cannot be enumerated. “Not found” and “not yours” throw the same error and return the same 404, so response codes leak nothing.
  • ✓Cross-actor access refused in practice. Two cookie jars: the owner reads its job (200); a different actor gets 404 on status, on the result bytes, and on cancel.
  • ✓Work directories are unpredictable. mkdtemp supplies the random suffix; the job id alone would be guessable, since a cuid embeds a timestamp and a counter.
  • ✓No original filename in a path. The id is sanitized to a safe segment before it reaches the filesystem.
  • ✓No traversal on cleanup. The removal helper refuses any path that is not under the processing root.
  • ✓Cleanup holds on every exit path. After roughly ten job runs across success, failure and a worker restart, the scratch root held 0 entries at mode drwx------.
  • ✓No internals reach users. Messages are derived from a fixed category set; no stack traces, filesystem paths, command-line arguments or service addresses. Diagnostic context is logged separately.
  • ✓No document contents recorded. The worker's event carries tool, mode, job id, owner type, result, attempt, byte counts, size buckets, duration, error category and page count — no filename, no paths, no text. A targeted scan for PDF and Ghostscript signatures in logs returned zero matches.
  • ✗The legacy status and download routes do not check ownership. Finding C above. Pre-existing, reachable in production, and demonstrated by fetching another owner's 78 KB output from a session-less client. The pipeline path is unaffected.
